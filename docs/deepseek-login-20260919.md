# DeepSeek 登录态复查（2026-09-19）

## 线上证据

- 检查时 API / Worker 镜像为 `v63`。DeepSeek 档案 #3、#4、#12、#13、#22 为 `login_required`，#21 为 `pending_login`。
- 六个档案均无已保存 Cookie / storageState。#3 最近四次采集返回 `needs_login`；历史数据库只保存错误名称，缺少拒绝原因。
- 单独恢复 #3 的 AgentBay Context 后仍跳转 `/sign_in`，没有有效 `userToken`。因此无法从现有线上状态复现一次有效登录到失效的完整过程，不能断言服务端令牌为何被拒。
- 代理供应商返回 `INVALID_KEY`，Worker 降级直连。此项需要有效的代理配置；本次没有替换代理密钥。

## 修复

1. DeepSeek 云端人工登录和采集采用相同的隔离上下文及档案 UA、语言、窗口和代理配置。其他引擎保留原有上下文创建策略。
2. DeepSeek 必须提供 `localStorage.userToken`；通用 `sessionid` 不再被当作该站登录凭证。
3. 登录成功前将完整 storageState 注入独立上下文，重新打开会话页并确认仍已登录且输入框可见。失败继续保留人工登录窗口，禁止报成功；取消仍有效。
4. 采集后仍确认已登录时保存刷新后的 storageState。使用凭证版本与账号状态条件更新，避免旧任务覆盖重新登录结果。
5. 连续登录检查失败时保留凭证，停止原先的自动清空行为。失效计数按凭证版本隔离；旧任务也不能把新登录或正在登录的账号改为冷却/失效。
6. 失败记录保存安全的登录判定类别和凭证存在信息，不记录令牌、Cookie 值或页面正文。
