# 产品深度审查:118 条改进意见(2026-09-19)

> 基于代码库、生产数据、竞品(透镜GEO)对标与真实运行事故的完整审查。
> 优先级:P0 = 影响可用性/可信度;P1 = 明显提升;P2 = 长期竞争力。
> 优先级汇总见文末「如果只做 10 件事」。

---

## A. 采集与数据供给(核心瓶颈,22 条)

1. **P0 账号池容量是全产品的天花板**:每档案 20 次/天 × 可用档案数 ≈ 40-60 次/天,而 51 题 × 5 引擎 = 255 次/轮。数据永远吃不饱,所有页面的"空"最终都追溯到这里。应做容量规划表:目标题数 × 引擎数 × 采样频率 ÷ 单账号日额 → 需要的账号数,并把它做成 admin 可视化。
2. **P0 尾部饥饿问题未根治**:26 个问题零数据就是因为调度按题目顺序派发、前排吃光额度。需要"最少覆盖优先"公平调度(7 天内无数据的问题优先入队),而不是手工归档老题目这种手术方案。
3. **P0 quota_blocked 收口后无补采机制**:任务落 quota_blocked 即终态,第二天配额恢复也不会自动补采欠账。应有"欠账账本"——按问题的最近成功时间排序,新配额优先还旧账。
4. **P0 豆包风控软拦截失败率 ~50%**(推荐位空回答/输入框消失/goto 超时三种形态),生产上基本靠运气。需要:失败形态自动归类、连续拦截自动降频、以及评估官方 API 通道(火山方舟)替代 DOM 采集的可行性。
5. **P0 文心(百度)实际上处于不可用状态**:UI 已迁移到 chat.baidu.com 搜索结果页、游客提交触发图形验证码、选择器全失效。要么投入一次完整校准(需登录态+新 DOM 分析),要么在引擎列表中显式标注"维护中",不要让用户以为有 5 引擎覆盖。
6. **P1 DeepSeek 登录态周期性失效**已发生 6+ 次,每次都静默变成 login_required。需要:失效前预警(session 年龄)、失效后 admin 告警推送,而不是等用户发现数据缺了。
7. **P1 引擎覆盖不均导致指标失真**:元宝/千问出数多、豆包/文心/DeepSeek 常缺,某问题的"提及率"实际是 2 个引擎的口径。所有三率展示应标注实际参采引擎数(分母透明)。
8. **P1 跨 IP 会话失效是平台级风险**:Cookie 绑定出口 IP,青果代理租约到期换 IP 就会集体 needs_login。应在代理租约到期前 N 小时告警并禁止跨租约复用 Cookie。
9. **P1 采集成功率没有产品化呈现**:admin 有引擎健康,但租户侧看不到"我的数据是 60% 引擎覆盖下算出来的"。建议每个页面角落给"数据覆盖度"徽标。
10. **P1 采集时段策略**:nextRunAt 随机化已有雏形,但应支持"跟随真实用户活跃时段"(工作时段密、深夜疏)以降低风控特征。
11. **P2 移动端 surface 完全缺失**:抖音/小红书/微信搜一搜是快消与美妆行业的主战场,竞品已覆盖。这是美妆个护报告说服力的硬伤。
12. **P2 国际引擎(Perplexity/ChatGPT/Gemini)未覆盖**:出海客户与 3C/跨境电商的刚需,可作为高客单增值包。
13. **P2 采集管道单点依赖 AgentBay**:Context 不持久化 Cookie 是平台限制(已用 DB 注入绕过),但 AgentBay 故障=全站停采。评估自建 Playwright 集群作为备份通道。
14. **P2 同题短期重复采集浪费额度**:同一问题 24h 内多品牌重复问(行业洞察影子品牌与租户品牌问同一题)。可做跨品牌的问题指纹缓存,相似问题共享采集或错峰。
15. **P1 每日配额重置时区是 UTC 还是本地?** daily_date=current_date 按库时区,与用户感知的"新的一天"可能错位 8 小时,容易造成"为什么还没恢复"的困惑。
16. **P2 采集成本不可见**:每 run 消耗代理时长+浏览器分钟+LLM 判定费,admin 应有成本报表,为定价调整提供依据。
17. **P1 失败重试的退避策略单一**:熔断 60s/池空 120s 固定间隔,且 MAX_DEFERRED=15 后收口。应按失败原因分类退避(needs_login 不重试、quota 用长退避)。
18. **P2 问题语义去重**:用户可能添加"20万SUV推荐"和"二十万预算SUV怎么选"两题,语义重复浪费 2 倍额度。入库时 LLM 相似度检测给提示。
19. **P1 采集并发=2 过保守**:SAE 单实例双并发,AgentBay 会话可并行。压测后提到 4-6 可让日额度更快消化。
20. **P2 证据保全合规**:OSS 里的 answer.json 含引擎完整回答,长期存储的版权/合规风险应有保留期限策略(如 90 天)。
21. **P1 影子品牌与租户品牌抢配额**:行业洞察采集(影子品牌)与租户采集共用全局每日上限。应给行业哨兵独立配额池或低优先级,避免平台内容生产挤占付费客户。
22. **P2 问题生效的采样频率语义**:freq=1 表示每天一轮全量,缺"每题独立频次"(核心题每天、长尾题每周)。

## B. 指标口径与数据质量(16 条)

23. **P0 口碑情绪得分口径粗糙**:得分=正面/有效,把中性算分母。中性占比 70% 时品牌显得"差"。应改为加权(正+1/中0/负-1)或分开呈现"净情绪"与"中性占比"。
24. **P0 小样本出结论**:3 条口碑回答就渲染"口碑天平"和情绪得分,统计上无意义。所有聚合模块应有最低样本门槛(N<10 显示"数据积累中"而非结论)。
25. **P0 LLM 口碑判定无人工抽检界面**:低置信样本进 audit pending 池,但产品里没有审核界面——池子只进不出。做一个简单的抽检页(展示回答原文+判定,一键纠正)。
26. **P1 综合名次=未上榜记 N+1 取中位数**:对 N(参采引擎数)敏感,引擎覆盖波动时名次跳变。至少在名次旁标注 N,或提供"仅计已上榜引擎"的替代口径开关。
27. **P1 环比箭头口径不严谨**:▲▼对比上一窗口同引擎,但两窗口样本量不同(昨天 3 引擎今天 5 引擎),变化可能只是覆盖变化。应只在两窗口引擎集合相同时显示环比。
28. **P1 竞品识别靠词库精确匹配**:别名配置不全就漏识别("理想L9"不算"理想汽车"已处理,但"小鹏""XPeng"这类需要用户手工补)。用 LLM 实体消歧做兜底判定。
29. **P1 自有信源只认官网单域名**:品牌在微信公众号/知乎机构号/百家号的内容都是"自有",现在全部算第三方。支持自有域名/账号组配置。
30. **P1 口碑印象词跨 run 重复计数**:同一条回答被多个引擎采集,同一印象词计 2 次。聚合时应按"去重后的独立证据"计数。
31. **P2 引用 URL 归一化不完整**:utm 参数剥离了,但 m.前缀与主域(auto.sina.cn vs sina.cn)未归并,信源榜被同族域稀释。
32. **P2 platform_domain_dict 无维护界面**:域名分类字典在库里,admin 没有编辑入口,新域名全落 "unknown"——报告里"unknown 平台被引 275 次"非常不专业。
33. **P1 证据摘要质量依赖首句启发式**:虽有 pickExcerpt 过滤,但 LLM 判定时已产出更好摘要,直接复用即可,不必两套逻辑。
34. **P2 时区展示混乱**:DB 存 UTC、页面 zh-CN、调度 Asia/Shanghai,admin 的"今日任务"与用户"今天"可能差 8 小时。统一声明产品时区。
35. **P1 数据回填靠手工脚本**:已写了 4 个一次性脚本(乱码回填/垃圾清理/口碑重判/配额重置)。这类数据修复应产品化为 admin"数据工具箱"。
36. **P2 榜单问题的答案时效性**:AI 回答引用的数据有滞后(销量榜是旧数据),报告应标注"AI 引用内容的时间偏差"作为分析维度——这本身就是洞察点。
37. **P1 三率的分母含 ok_empty**:"有效回答"=有答案+空答案。空答案(引擎拒答)应细分展示,它可能是"该问题无行业内容"的信号。
38. **P2 口碑词与排名词的交叉分析缺失**:"口碑差的题恰好排名也低"这类相关性是最有价值的洞察,现在两个模块完全隔离。

## C. 产品功能补全(20 条)

39. **P0 会员端洞察列表页缺失**:/insights/[id] 详情页存在但没有任何列表入口,会员发现不了报告。建 /insights 列表页(已发布报告卡片流)并在导航露出。
40. **P0 报告 PDF 质量未验证**:insight-pdf 渲染链路存在但未端到端核对排版(字体/图表截断/分页)。PDF 是销售物料,应逐页 QA。
41. **P1 报告无期次对比**:每周一期但看不到"本期 vs 上期"的变化(哪些品牌升了)。加一个 diff 块是报告价值翻倍的改动。
42. **P1 洞察报告分享能力为零**:无分享链接/海报/水印。公开页有了但没传播工具。做"生成分享海报(二维码+核心图表)"。
43. **P1 行动清单无闭环**:行动项只能看不能标记完成/跟踪效果。加勾选状态与"关联指标变化"回看。
44. **P1 报告自定义品牌可见性**:客户可能想给老板/投资人看"只含我竞品"的报告版本。
45. **P2 报告模板多样化**:目前单一 blocks 顺序。支持"快报版(1页)/完整版"两种深度。
46. **P2 报告定时邮件/企微推送**:周一自动生成后推送给订阅用户,这是留存钩子。
47. **P1 监控问题推荐器**:用户建品牌后不知道该配什么题。按行业模板+品牌挖掘结果推荐 20 题(行业洞察的问题生成器已具备能力,复用即可)。
48. **P1 竞品自动发现的转正流**:competitor_candidates 池在积累,但 admin/租户侧没有"发现新竞品→确认加入口径"的界面闭环。
49. **P2 品牌 SEO 健康检查**:接入页面收录/结构化数据检查(GSC API),把"内容问题"与"可见度问题"归因区分。
50. **P2 舆情告警**:负面印象词突增(如"苏丹红"事件)实时告警,这是快消客户付费的核心场景。
51. **P1 引用源 per-engine 交叉矩阵**:竞品有"品牌×引擎被引矩阵",我们只有全局信源榜。数据已有(citation_facts 有 engine 列),只差聚合与展示。
52. **P2 信源新增/持续/流失对比**:竞品的"本期新增被引/持续被引/流失"分析,指导内容维护优先级。
53. **P1 采集状态页缺"下次采集倒计时"**:next_run_at 在库里,页面没展示,用户不知道数据何时更新。
54. **P2 多品牌对比视图**:同账号多品牌(集团客户)横向对比页。
55. **P2 API 开放**:企业客户把指标拉进自己 BI。至少提供只读 API + token 管理。
56. **P1 导出增强**:CSV 有了,补 Excel(多 sheet:矩阵+漏斗+引用)与 PNG(图表)。
57. **P2 通知中心**:采集完成/报告发布/账号失效站内信,现在全靠刷新发现。
58. **P2 历史口径回放**:口径版本快照在存,但没有"按历史口径重算当前数据"的查看器,审计价值没兑现。

## D. 产品设计与体验(18 条)

59. **P0 新用户冷启动体验割裂**:注册→建品牌→配问题→等采集(2 小时+)→看空页面。中间无进展反馈。应做 onboarding 进度条(品牌✓问题✓采集中 12/50✓)。
60. **P0 示例数据体验缺失**:销售演示/新用户看不到"数据长什么样"。做一键演示品牌(内置样本数据,标注 DEMO 水印)。
61. **P1 空状态与错误状态不一致**:有的页面给引导(口碑页 A5 对策),有的只给"暂无数据"。统一空状态规范(是什么/为什么/下一步)。
62. **P1 时间范围无自定义**:只有 1/7/30 天。日期区间选择器是分析工具标配。
63. **P1 筛选状态不持久**:引擎/问题筛选刷新即丢。存 URL query 或 localStorage。
64. **P1 表格与图表的信息密度失衡**:排名矩阵信息密度好,但仪表盘大片留白。对标竞品的紧凑数据风(他们的矩阵一行 9 列)。
65. **P2 移动端复查**:之前做过一轮适配,但新增页面(向导/品牌资产/行动清单)未复查。
66. **P2 深色模式**:分析工具用户偏好明显,Tailwind 已具备条件。
67. **P1 口碑原文证据 100 条一次渲染**:SAMPLE_LIMIT 提到 100 但无分页,页面会卡。虚拟列表或分页。
68. **P1 图表交互性弱**:SVG 图表无 tooltip/点击下钻(点柱子看明细 run)。
69. **P2 全局搜索**:跨问题/报告/资料的 cmd+k。
70. **P1 品牌切换器埋得太深**:多品牌用户每次去顶栏切。矩阵页内嵌品牌 tab。
71. **P2 操作撤销**:删除问题/资料/报告无二次确认或软删除(报告删除是硬删)。
72. **P1 加载态与错误态的区分**:骨架屏后如果是接口 500,部分页面白屏。ErrorBoundary + 重试按钮。
73. **P2 文案口径统一**:"提及率/上榜率/首推率"与"三率"混用;"品牌资产/品牌资料/品牌档案"三个叫法并存。
74. **P1 admin 与租户视图的心智分离**:行业洞察生成器在 admin,但会员看到的洞察列表页(待建)风格应完全不同(消费端 vs 生产端)。
75. **P2 首页(官网)与产品的视觉断层**:官网在做动效,但产品内还是朴素表格风,品牌感不连贯。
76. **P2 键盘与无障碍**:表格操作、模态框 Esc、aria 标签系统性补齐。

## E. 商业化与市场(16 条)

77. **P0 定价与成本模型脱节**:¥199/月标准档,但单品牌 50 题 × 5 引擎 × 日采的成本(账号+代理+LLM)可能吃掉大半毛利。做单位经济模型,问题数/引擎数至少一项要限量或加价。
78. **P0 无免费试用/演示通道**:注册后必须自己配品牌才能看到价值,转化漏斗断裂。示例数据(60 条)+ 7 天全功能试用。
79. **P1 行业报告是最佳获客资产但没被利用**:公开详情页无 SEO 元数据(标题/描述/OG 图)、无"生成你的品牌报告"CTA、未提交搜索引擎收录。
80. **P1 竞品对比页缺失**:对透镜GEO 的差异化(口径可复现/证据链/LLM 洞察深度)应做成官网对比页。
81. **P1 客户案例空白**:理想汽车数据已跑通,脱敏后即是首个案例。
82. **P2 按需单份报告售卖**:¥99/份行业报告,低门槛获客再转订阅。订单系统已具备(orders)。
83. **P2 渠道/代理体系**:代理商白标后台,报告带客户 logo。
84. **P1 套餐升级触发点**:额度用尽只在采集侧收口,用户无感知。配额页加"升级解锁"引导与用量预警(80%)。
85. **P2 发票与对公支付**:微信/支付宝个人支付有了,企业采购需要对公转账+开票流程。
86. **P1 续费提醒与流失挽回**:periodEnd 到期无提醒,静默失效=流失。到期前 7 天站内+短信。
87. **P2 内容营销节奏**:行业洞察周更(已自动化)应同步到公众号/知乎,形成获客飞轮——缺的是自动分发环节。
88. **P1 销售线索捕获**:公开报告页的"下载完整版"应要求留资(手机号),这是销售线索源头。
89. **P2 品类优先级**:美妆/家电/新能源的数据资产已起步,应聚焦 2-3 个行业打深(行业问题库更全、报告更权威),而非全行业铺开。
90. **P2 竞对价格监控**:透镜GEO 定价与功能变动追踪,作为产品决策输入。
91. **P1 价值证明报表**:月度"你的品牌可见度变化+带来的动作与效果"邮件,让客户看见续费理由。
92. **P2 早期客户定价实验**:5 个种子客户免费换深度反馈与案例授权。

## F. 技术架构与可靠性(14 条)

93. **P0 单点无 HA**:API/worker 各 1 实例,Redis/RDS 单实例。调度器有 advisory lock 支持多实例,但 API 的 dig in-memory 去重、登录管理器都是单实例假设。至少 worker 扩 2 实例验证互斥。
94. **P0 无告警体系**:worker CrashLoop、队列积压 300+、账号池耗尽、代理失效——全部静默,每次都是用户先发现。接钉钉/企微 webhook 分级告警。
95. **P1 部署竞态**:并行会话 + deploy.sh 版本号赛跑已发生 3 次(v39/v50/v51 冲突)。加 ACR tag 锁或部署互斥文件。
96. **P1 数据库迁移无流水线**:手工 psql 执行 SQL,易漏易错。迁移纳入 CI(db:migrate)与发布前置检查。
97. **P1 LLM 成本无预算控制**:口碑/实体/行动项/洞察每 run 调 GLM,无 token 计量与月度预算熔断,被滥用或失控时无保护。
98. **P2 查询性能审查**:matrix/rankings 的 SQL 含多处子查询与 filter,品牌数据量到 10 万 run 量级需要执行计划审查与物化(日结层已有,利用率可提高)。
99. **P2 前端轮询改 SSE**:采集状态 10s 轮询、洞察 2.5s 轮询,量大后 API 压力与体验都不佳。
100. **P1 权限模型单一**:只有 user/admin。企业客户需要"老板只看报告/运营全权"的角色,以及账号下多成员。
101. **P1 越权面自查**:insights 的资料删除已补归属校验,但应系统性做一次 IDOR 审计(所有 :id 端点过一遍归属检查)。
102. **P2 备份演练**:RDS 自动备份存在但从未演练恢复;OSS 证据无备份策略。
103. **P2 前端错误上报**:无 Sentry 类前端异常采集,用户侧白屏我们不知道。
104. **P1 构建时间 10 分钟**:全量 pnpm build 每次部署都全量。分层缓存(依赖层/包层/应用层)+ 按变更范围跳过无关 app 构建。
105. **P2 测试覆盖**:指标计算有单测,但采集适配器(风控形态)、调度公平性、计费边界缺测试。适配器的"失败形态样本库"(豆包 5 种形态)应固化为回归用例。
106. **P2 环境一致性**:本地 .env.debug 与 SAE 环境变量手工同步,易漂移。用配置中心或至少 env 导出比对脚本。

## G. 洞察报告专项(12 条)

107. **P1 行业洞察的数据厚度门槛**:8-30 条回答生成的报告,头部建议标注"试读版/数据积累中",避免低样本报告损伤专业形象(口碑 14% 正面率那条其实是 7 条样本)。
108. **P1 报告数据来源标注**:每份报告页脚应有"基于 N 条真实引擎回答/覆盖 M 引擎/采集窗口"的透明度声明——这既是可信度也是差异化卖点。
109. **P2 LLM 撰稿的事实校验层**:takeaways 偶有数字近似复述偏差,可加一道"引用数字与聚合事实比对"的校验,不符则重写。
110. **P1 行业品牌推荐的可维护性**:AI 推荐一次即静态,行业格局变化(新品牌崛起)不会自动提示。月度 diff 推荐新品牌。
111. **P2 报告版本管理**:重新生成直接覆盖 blocks,上期内容不可回看。期次留档(表已支持多行,但 runIndustry 复用最新一行)。
112. **P2 影子品牌的隐私边界**:行业洞察采集的问题会真实进入引擎,问题文案应避免引导性表述(已基本做到,需成文规范)。
113. **P1 向导步骤④的前置校验**:品牌/问题未就绪或零数据时,「生成」按钮应禁用并提示缺什么(现在是生成后才报错"没有监测品牌")。
114. **P2 报告多语言**:出海客户场景,标题/摘要双语言版本。
115. **P1 洞察与品牌产品的交叉导流**:报告页"你的品牌不在此列?免费检测"→注册流程,形成获客闭环。
116. **P2 行业基准线**:报告应给出"全行业平均提及率/首推率"基准,让品牌知道相对位置而非绝对值。
117. **P1 主编综述的素材扩展**:目前只喂结构化事实+品牌资料,可加入"本期热门问题 Top3 的典型回答摘录"让叙事更鲜活。
118. **P2 报告合规免责**:涉及竞品负面(克价争议/苏丹红)的表述需法务审核模板与"数据来源声明",规避商誉纠纷。
